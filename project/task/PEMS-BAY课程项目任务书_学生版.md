# 《交通大数据分析与应用》PEMS-BAY课程项目任务书

## 一、项目基本信息

| 项目 | 要求 |
|---|---|
| 考核形式 | 课程项目考查 |
| 分组方式 | 全班5组，每组4—5人 |
| 项目数据 | 教师统一提供的PEMS-BAY课程数据包 |
| 项目分配 | 教师从8个项目中为本学期5个小组各分配1项 |
| 项目汇报 | 第12周课堂汇报，每组15分钟：10分钟陈述、5分钟问答 |
| 平时成绩 | 课程总成绩的20%，包括考勤和课堂表现 |
| 小组汇报 | 课程总成绩的30%，组内成员同分 |
| 个人报告 | 课程总成绩的50%，每人独立提交并独立评分 |

## 二、项目目标

本项目不以“使用尽可能复杂的算法”为目标。各组需要从交通管理场景出发，把现实需求转化为可以利用数据回答的问题，再用适当的方法建立证据链。

> 管理场景 → 决策需求 → 交通问题 → 分析对象 → 指标与方法 → 结果验证 → 结果解释 → 局限 → 建议

完成项目后，应能够：

1. 识别场景中的管理主体、决策对象和现实约束；
2. 把宽泛需求转化为一个主问题和2—3个相互衔接的子问题；
3. 正确理解5分钟速度、检测站、空间位置和距离关系；
4. 选择与问题匹配的分析单位、指标、基准和方法；
5. 解释结果在交通运行和管理上的含义，而不是只罗列图表和模型指标；
6. 说明数据不能支持什么，并提出与证据强度一致的建议。

## 三、数据边界

所有小组使用教师统一发布的 `学生数据包`。学生无需自行注册或下载数据，也不得用其他版本替代课程数据。

课程数据包括：

- 325个高速公路检测站的5分钟平均速度；
- 检测站编号、列顺序和经纬度；
- 部分有向站点对的距离关系；
- 数据字典、已知质量问题和读取示例。

数据时间范围为2017年1月1日至6月30日。主数据有52,116个时间点和325个检测站速度列。具体字段、单位和已知问题见《PEMS-BAY课程数据包说明》。

本数据没有流量、占有率、事故、天气、施工、车道、道路方向或管理措施字段。因此：

- 可以分析速度变化、拥堵状态、时间规律、空间关联、预测、预警和数据冗余；
- 不能仅凭本数据断言低速由哪一种原因造成；
- 不能估计完整交通流基本图、道路容量或车辆总延误；
- 不能把相关关系直接写成管理措施的因果效果。

## 四、所有小组的共同任务

每组必须完成以下内容：

1. 明确管理主体需要作出的决定，而不是先选择算法；
2. 提出一个主问题和2—3个子问题；
3. 明确分析对象、观测单位、空间范围、时间范围和核心指标；
4. 说明如何处理0值和2017年3月12日的时间缺口；
5. 建立一个简单、透明的比较基准或判断规则；
6. 选择一种主要分析方法，并解释为什么适合本组问题；
7. 至少完成一项方法比较、阈值敏感性、跨月检验或其他稳健性检查；
8. 用关键图表和计算结果回答问题；
9. 解释结果在哪些站点、日期或条件下成立，以及为何值得关注；
10. 说明至少两项具体局限，并提出至少两项有证据支撑的管理建议。

项目问题不能只写成“使用随机森林预测”“采用聚类算法分析”或“绘制热力图”。算法和图表是回答交通问题的工具，不是项目目标本身。

## 五、八个项目场景

### 项目一：有限预算下的拥堵治理排序

#### 场景

道路管理部门下一阶段只能优先治理三个检测站附近的拥堵问题。有人建议直接选择平均速度最低的三个站点，也有人认为还应考虑拥堵发生频率、持续时间、严重程度以及排序在不同月份是否稳定。管理部门希望得到一套透明、可解释、能够复核的优先顺序。

#### 你们需要解决的核心问题

怎样把“优先治理”转化为有依据的排序？最终推荐的三个位置是否会因为拥堵阈值、指标权重或时间范围改变而大幅变化？

#### 入手提示

- 先说明“拥堵”和“一个位置”的定义；
- 比较只看平均速度与综合考虑频率、持续时间、严重程度的差异；
- 排名很接近时，不要把细小数值差异写成确定结论；
- 管理建议应说明优先级适用于何种时间和运行状态。

### 项目二：早晚高峰是否需要差异化管理

#### 场景

交通运行中心目前在工作日早高峰和晚高峰采用相同的监测阈值、信息发布方式和人员安排。管理人员怀疑，一些位置主要在早高峰出现问题，另一些位置主要在晚高峰出现问题，还有一些位置的低速并不集中在传统高峰时段。

#### 你们需要解决的核心问题

早晚高峰的运行问题是否具有相同的空间分布和稳定性？哪些位置适合统一管理，哪些位置需要差异化安排？

#### 入手提示

- 自行说明工作日、早高峰和晚高峰的时间边界；
- 不只比较均值，还应关注低分位速度、波动或低速发生比例；
- 检查不同月份是否得到相近结论；
- 只能说明速度模式差异，不能从现有数据推断通勤方向或拥堵原因。

### 项目三：特殊日期的运行保障识别

#### 场景

管理部门希望提前制定特殊日期的值守方案，但没有一份可靠的“异常日期清单”。某一天网络平均速度偏低，可能是全网普遍异常，也可能只是少数位置严重低速；反之，网络平均速度正常，也可能掩盖局部问题。

#### 你们需要解决的核心问题

怎样识别与通常同类日期明显不同的运行日？这些异常是全网性的、局部性的，还是仅集中在特定时段？

#### 入手提示

- 先建立“通常工作日”“通常周末”等比较基准；
- 不要只用一个网络平均值判断异常；
- 对识别出的日期进一步检查日内曲线和空间分布；
- 没有外部事件数据时，只能称为“异常运行日”，不能自行认定事故、天气或节假日是原因。

### 项目四：拥堵事件的持续与恢复管理

#### 场景

运行人员发现，不同低速事件的处置价值并不相同：有些只是短暂波动，有些持续很久；有些速度很快恢复，有些在恢复后又反复下降。管理部门希望把连续的5分钟记录转化为可解释的“拥堵事件”，并识别更值得关注的事件类型和位置。

#### 你们需要解决的核心问题

什么样的连续低速可以视为一次拥堵事件？不同事件在持续时间、严重程度、恢复过程和重复发生方面有何差异？

#### 入手提示

- 明确事件开始、结束、最短持续时间和短暂间断的处理规则；
- 区分事件发生频繁、持续很久和程度很深三种概念；
- 检查0值和时间缺口是否会人为切断或延长事件；
- 讨论一种统一事件规则是否适合所有站点。

### 项目五：相邻站点能否提供拥堵传播预警

#### 场景

某检测站出现明显速度下降时，运行人员希望知道附近站点的变化是否能够提前10—30分钟提供信号。如果相邻站点只是同步变化，预警价值可能有限；如果某些站点稳定领先，则可用于加强监测。但坐标接近、距离关系和速度相关并不等同于真实交通传播。

#### 你们需要解决的核心问题

对一个具有明显低速变化的中心站点，哪些相连站点与其变化最相关？这种关系是同步、领先还是滞后？是否稳定到足以形成预警建议？

#### 入手提示

- 选择一个有足够低速事件的中心站点和若干相连站点；
- 比较空间距离、同时相关和滞后关系，不要只展示地图；
- 在多个事件或月份中检查领先关系是否稳定；
- 不能把统计领先直接写成道路上下游传播或因果影响。

### 项目六：未来15分钟交通信息发布

#### 场景

交通信息平台计划发布未来15分钟的速度信息。目前系统最简单的做法是把当前速度作为15分钟后的预测。管理部门希望判断，引入更多历史信息和时间特征是否带来实际改善，以及预测在哪些站点、时段和交通状态下容易失效。

#### 你们需要解决的核心问题

主要方法能否稳定优于简单基准？总体误差是否掩盖了拥堵时段或特定站点的较大误差？

#### 入手提示

- 明确输入时刻和预测目标，避免使用未来信息；
- 按时间顺序划分训练、验证和检验数据；
- 至少与“当前速度直接延续”比较；
- 除总体误差外，还应分站点、分时段或分交通状态分析误差。

### 项目七：每个时段最多核查三个位置的拥堵预警

#### 场景

交通管理中心每15分钟最多只能重点核查三个位置。漏掉真正的严重低速会延误处置，但误报过多会占用有限资源。管理部门需要的不是无限制地报出所有风险位置，而是一套在资源上限下能够执行的风险排序。

#### 你们需要解决的核心问题

如何定义未来15分钟的严重低速风险，并在每个时段最多选择三个位置？这套规则在漏报和误报之间作出了怎样的取舍？

#### 入手提示

- 明确严重低速标签和风险预测时点；
- 将准确率与“每时段最多三个位置”的决策约束分开考虑；
- 评价Top-3命中、漏报、误报和无事件时段的表现；
- 最终阈值或规则只能在训练、验证阶段确定，不能在检验数据上反复调整。

### 项目八：有限维护资源下的检测站优先级

#### 场景

数据平台主管部门只能优先维护少量检测站。某些站点与附近站点高度相似，暂时缺测时可能容易估计；另一些站点记录了独特的运行变化，一旦失效就会造成较大信息损失。管理部门希望同时考虑站点的数据独特性、空间覆盖和交通运行重要性。

#### 你们需要解决的核心问题

怎样判断一个站点是“可由其他站点替代”还是“信息不可替代”？如果只能优先维护五个站点，应如何形成排序并验证其合理性？

#### 入手提示

- 先区分“交通问题严重”与“数据不可替代”两个概念；
- 可以模拟某站点数据不可用，再用其他站点估计其速度；
- 比较只用最近站点、只用高相关站点和综合选择的差异；
- 说明维护排序对候选范围、邻居数量或分析月份是否稳定。

## 六、小组汇报要求

### 1. 时间与形式

- 第12周课堂进行；
- 每组15分钟；
- 10分钟陈述；
- 5分钟问答；
- 10分钟到时停止陈述并进入问答。

### 2. 建议结构

1. 场景、管理主体与需要作出的决定；
2. 主问题、子问题和证据需求；
3. 分析对象、时间空间范围和数据质量处理；
4. 基准、主要方法和验证设计；
5. 3—5幅关键图表与主要结果；
6. 对结果的交通含义和条件的解释；
7. 局限、管理建议和最终回答。

汇报开头应清楚展示：

> 场景 → 决策 → 分析对象 → 问题 → 需要什么证据

### 3. 小组提交材料

每组提交：

- 汇报PPT；
- 可运行的代码或Jupyter Notebook；
- 运行说明和必要的相对路径说明。

代码或Notebook不单独设置成绩比例，但结果无法复核、路径只在某一位同学电脑上可运行，或运行结果与PPT不一致，都会影响方法与结果可信度的评价。

## 七、个人数据分析报告

### 1. 基本要求

- 每位学生独立提交一份报告；
- 正文建议3000—5000字，图表、参考文献和附录不计入正文篇幅；
- 可以使用本组共同完成的数据处理、代码、计算结果、模型输出和图表；
- 报告正文及所有分析性文字必须独立撰写；
- 文件命名、提交格式和截止时间以课程平台通知为准。

### 2. 参考结构

#### （1）场景理解与问题表述

说明管理主体、决策需求、分析对象、时空范围、主问题和子问题。不得以算法名称代替交通问题。

#### （2）数据和质量处理

说明观测单位、使用文件、核心字段、单位、时间范围、站点范围，以及0值、时间缺口和其他异常的处理规则。不需要自行下载数据或展开介绍数据来源。

#### （3）方法选择与验证设计

说明简单基准、主要方法、评价指标、数据划分和稳健性检查，并解释这些选择为什么适合本报告的问题。

#### （4）图表与主要结果

图表应具有独立撰写的标题、坐标名称、单位、图注或表注。正文应说明图表反映了什么，不得只写“结果如图所示”。

#### （5）结果的深入解释

解释关键结果为什么值得关注、不同结果是否相互支持、在哪些站点或条件下成立、是否具有实际管理意义，以及如何回答前文问题。

#### （6）局限性讨论

具体讨论数据字段、指标定义、方法、验证范围和推断边界，并说明这些局限可能使结论偏向什么方向。不得只写“数据有限”“模型还可以改进”。

#### （7）交通管理建议

建议应明确管理对象、适用条件、实施方式和可能风险，并与分析结果直接对应。不得提出数据无法支持的因果性或普遍性结论。

#### （8）结论

直接回答主问题，区分已经得到的证据、仍然不能判断的内容和后续需要补充的数据。

## 八、组内共用与独立撰写边界

### 1. 可以组内共用

- 小组共同形成的核心问题和分析框架；
- 课程数据、数据处理代码和Notebook；
- 计算结果、模型输出、图和表；
- 共同使用的参考文献。

### 2. 必须独立撰写

- 对场景、决策需求和问题边界的说明；
- 数据和方法说明；
- 图表标题、图注、表注及正文中的图表解释；
- 结果的深入解释；
- 局限性讨论；
- 交通管理建议；
- 结论及其他正文。

允许采用相同的参考结构，但不得共同撰写正文后拆分，不得复制组内成员文字，也不得仅替换同义词形成所谓“独立报告”。

每份报告应包含以下声明：

> 本报告所使用的数据处理代码、计算结果、模型输出及图表由小组共同完成；报告正文、图表标题与注释、结果解释、局限性讨论、交通管理建议及结论由本人独立撰写。

## 十、提交前检查

### 小组检查

- [ ] 开头明确了管理主体和需要作出的决定；
- [ ] 主问题可以用现有数据回答，没有用算法名称代替问题；
- [ ] 0值和时间缺口处理已经说明；
- [ ] 有简单基准和至少一项稳健性检查；
- [ ] 图表直接回答问题，坐标、单位和图注完整；
- [ ] 没有把相关性写成因果性；
- [ ] PPT可在10分钟内完成；
- [ ] 代码使用相对路径并能从头运行。

### 个人报告检查

- [ ] 正文为本人独立撰写；
- [ ] 图表标题、图注、结果解释、局限和建议均为本人独立撰写；
- [ ] 结果解释不只是重复数值；
- [ ] 每条管理建议都能对应到报告中的证据；
- [ ] 结论区分了“已发现”“不能判断”和“仍需补充”；
- [ ] 已加入独立撰写声明。
